## 1. 内存分配的核心概念

**内存分配 Memory Allocation**：程序为变量、对象或数据结构获取存储空间的过程。  
**释放 Deallocation**：不再需要存储时归还/回收，使其可被复用。

| 概念 | 快速理解 |
|---|---|
| 静态存储 | 如 C 的全局/静态对象，通常在程序运行整个期间存在 |
| 自动存储 | 如 C 语言的普通局部变量，随作用域/函数调用管理 |
| 动态存储 | 程序运行时按需分配，例如 C 的 `malloc`、C++ 的 `new` |
| 栈内存 Stack | 常用于调用帧、局部变量等；按调用层级组织 |
| 堆内存 Heap | 常用于动态对象；生命周期往往独立于当前函数调用 |
| 生命周期 Lifetime | 对象从创建到销毁的时间范围 |

**注意**：栈/堆是常见实现概念，不是所有语言和变量都严格遵循“局部一定在栈、数组一定在堆”。例如 Python 对象通常由运行时管理，局部变量可能只是对堆对象的引用。

## 2. 内存泄漏 Memory Leak（A）

**内存泄漏**：申请/占用了内存，但由于没有正确释放，或因仍被不必要的引用保留而无法回收，导致程序长期持有不再需要的存储。

**笔经选择题经典场景**：在循环中不断动态分配内存而没有释放。

```c
#include <stdlib.h>
void example(void) {
    for (int i = 0; i < 10000; ++i) {
        int *p = malloc(1000 * sizeof(int));
        if (p == NULL) return;
        /* 使用 p */
        /* 错误：这里忘记 free(p); */
    }
}
```

每轮局部指针 `p` 结束作用域后不再可用，但那块 `malloc` 内存没有 `free`，就是典型泄漏。

**正确方向**：
```c
int *p = malloc(1000 * sizeof(int));
if (p != NULL) {
    /* 使用 p */
    free(p);
    p = NULL;
}
```

C++ 使用 `new`/`delete` 和 `new[]`/`delete[]` 成对管理；在现代 C++ 更鼓励 RAII、智能指针与标准容器。

## 3. 内存泄漏、越界、悬空指针：三者不一样（A）

| 情况 | 本质 | 例子 |
|---|---|---|
| Memory Leak 内存泄漏 | 不再需要的空间未正常释放/回收 | `malloc` 后忘记 `free` |
| Out-of-bounds 越界 | 访问数组合法范围外的地址/下标 | 长度为 5 却写 `a[5]` |
| Dangling Pointer 悬空指针 | 指针指向已释放/已失效对象 | `free(p)` 后继续使用 `p` |
| Use-after-free 释放后使用 | 访问已经释放的内存 | `free(p); *p=1;` |
| Double Free 重复释放 | 同一块内存被重复释放 | `free(p); free(p);` |
| Stack Overflow 栈溢出 | 调用栈过深或栈空间耗尽 | 无终止条件的递归 |

**考题陷阱**：“数组越界一定会造成内存泄漏”——**错**。越界主要是非法访问问题；泄漏主要是内存所有权/释放问题，两者可能同时发生，但没有必然关系。

## 4. Garbage Collection（GC）（A）

**垃圾回收**是运行时自动识别并回收**不再可达**（或不再被需要、取决于具体机制）对象的内存的过程。

- Java：使用垃圾回收管理许多堆对象；
- Python：CPython 主要采用引用计数并辅以循环垃圾回收机制；
- C/C++：常见手动内存管理机制；现代 C++ 可通过 RAII/智能指针实现自动资源管理。

**GC 能做什么**：减少大量忘记释放对象所造成的内存回收负担。  
**GC 不能保证什么**：不能完全杜绝**逻辑性内存泄漏**。例如某个不断增长的全局列表一直保存本已不用的对象，它们仍“可达”，回收器就不会把它们当垃圾。GC 也不保证程序更快，不会自动修复数组越界，也不会降低算法的大 O 复杂度。

### 高频对错题

1. “Memory leaks only happen in C/C++.” → **错**。  
2. “Garbage collection always prevents every memory leak.” → **错**。  
3. “Repeatedly allocating without release can cause a leak.” → **对**。  
4. “GC prevents array out-of-bounds.” → **错**。  
5. “Not releasing dynamically allocated memory can cause a leak.” → **对**。  
6. “A fixed-size local array always causes a leak.” → **错**。

**资料注意**：个别笔经把“GC 可以防止内存泄漏”直接标记为正确。准确表述应是“GC 能自动回收不可达对象，**降低**某些泄漏风险，但不能保证完全杜绝内存泄漏”。

## 5. 递归空间复杂度与内存分配的联系（B）

即使算法没有新建列表，也可能因递归占用空间：
```python
def countdown(n):
    if n == 0:
        return
    countdown(n-1)
```
最多同时存在 `n` 层调用，额外调用栈空间通常 `O(n)`。  
相比之下，一个只使用固定数量局部变量的迭代循环可做到 `O(1)` 额外空间。

**时间复杂度**与**空间复杂度**分别描述运算次数与额外存储需求，不能混为一谈。

## 6. 口头表述与迷你自测

英文模板：
- *“A memory leak happens when memory is allocated but is not properly released or reclaimed when it is no longer needed.”*
- *“Garbage collection reclaims unreachable objects, but it cannot prevent every logical memory leak.”*

**自测**：
1. `malloc` 后失去指针且没 `free`，属于什么？**内存泄漏**。  
2. `free(p)` 后继续解引用 `p`，属于什么？**释放后使用/悬空指针**。  
3. Java 有 GC 就绝无内存泄漏吗？**不是**。  
4. `n` 层递归调用常占多少额外调用栈？**`O(n)`**。  
5. GC 是否能保证代码不会数组越界？**不能**。

**掌握标准**：看到一组英文定义题，能精准区分 allocation、leak、GC、out-of-bounds，且不会把“自动回收”理解为“万无一失”。

## V2｜原始资料真题补全

### 1. 变量、栈、堆、指针、生命周期：真实含义（【往届代码题】）

**先区分两种“栈”**：数据结构中的栈是 LIFO 逻辑；程序的**调用栈（Call Stack）**负责保存函数调用帧（返回地址、局部状态等），两者概念相关但不应混为同一个对象。

C 代码例：
```c
#include <stdio.h>
void change_value(int x) {
    x = 99;                // 只修改局部副本
}
void change_by_pointer(int *p) {
    *p = 99;               // 修改指针指向的实际对象
}
int main(void) {
    int x = 5;
    change_value(x);
    printf("%d\n", x);    // 5
    change_by_pointer(&x);
    printf("%d\n", x);    // 99
    return 0;
}
```

记忆：`&x` 取 x 地址；`p` 存地址；`*p` 访问地址指向的值。C++ 里也可以用 `int& ref` 形式把实参作为引用传入。遇到 `swap(a,b)` 要看参数是按值、指针还是引用。

**内存区域**（常见实现，不能把它当作所有语言的硬规定）：
- 静态/全局存储：如 C 的全局变量、`static` 存储期对象；
- 自动存储：如 C 的普通局部对象，通常随调用帧结束生命周期；
- 动态存储：如 `malloc`、`new` 申请的存储，释放时机由程序或管理机制决定；
- Python 中变量常是指向运行时对象的**绑定名称**，引用的目标对象不等同于 C 的栈上局部整数。

### 2. Memory Leak、GC 与四类典型错误（【26Fall 正式批】）

| 术语 | 解释 | 典型例子 |
|---|---|---|
| Allocation 内存分配 | 向运行时/系统申请存储 | `malloc(n)` / `new` |
| Deallocation 释放 | 使存储可重新使用 | `free(p)` / `delete` |
| Memory Leak 内存泄漏 | 不再需要却未释放或持续被引用而无法回收 | 循环中只分配不释放 |
| Dangling Pointer 悬空指针 | 指向已失效对象的指针 | `free(p)` 后继续 `*p` |
| Buffer Overflow 越界访问 | 读写合法范围之外的位置 | `arr[5]` 但长度只有 5 |
| Double Free 重复释放 | 同一分配块释放两次 | `free(p);free(p)` |
| Use After Free | 已释放后又访问 | `free(p);p[0]=1` |

**面试答法**：*“Memory leaks are about unreclaimed storage; buffer overflows are invalid memory accesses. They are different bugs.”*

**GC（垃圾回收）**：
- Java 会自动检测许多不可达堆对象并回收；**仍可能有逻辑性内存泄漏**，例如全局列表一直保存失去业务用途的对象。
- CPython 主要用引用计数并辅以循环垃圾收集，不是“完全没有 GC”。
- C/C++ 通常不内建 Java 风格的自动跟踪 GC，但 C++ 有 RAII / 智能指针等资源管理手段。
- GC 不自动修复越界、不会保证程序运行更快、也不会优化算法时间复杂度。

**原笔经里的措辞问题**：有一题把 “GC prevents memory leaks” 选为正确，准确说法应是“GC **减少部分忘记释放不可达对象导致的泄漏**，但无法完全防止所有逻辑性泄漏”。作答时优先遵守题干对比意图，同时避免绝对化表达。

### 3. C++ RAII、智能指针和 Python 资源管理（【资料知识点加深】）

RAII（Resource Acquisition Is Initialization）把资源的获取/释放与对象生命周期绑定：对象离开作用域时执行析构函数，标准容器和智能指针可自动释放资源。例如：

```cpp
#include <memory>
#include <vector>
void example() {
    std::vector<int> a(1000);             // 自动管理存储
    auto p = std::make_unique<int>(42);   // 独占所有权
} // 退出作用域，释放资源
```

- `unique_ptr`：排他所有权；`shared_ptr`：引用计数共享所有权，循环引用可能需要 `weak_ptr` 打破。
- Python 的文件对象适合 `with open(...) as f:` 自动关闭；文件句柄等**外部资源**不能只靠“GC 总会回收”来保证及时清理。

### 4. 操作系统与线程：对应原始面经的术语追问（【口头补全】）

原始资料提到“操作系统术语”，但未给确切问题，所以补最常见的基础层：

- **Process 进程**：运行中的程序实例，通常拥有独立的虚拟地址空间。
- **Thread 线程**：进程内的执行单元，同进程线程通常共享地址空间；各有自己的栈和执行状态。
- **Context Switch 上下文切换**：CPU 从当前任务切换到另一任务，保存/恢复执行状态，会有开销。
- **Race Condition 竞态条件**：并发执行结果依赖不可预知的时序；`counter += 1` 不一定天然线程安全。
- **Lock/Mutex 互斥锁**：保护临界区；不当使用可能出现死锁。
- **Virtual Memory 虚拟内存**：提供进程隔离的地址空间，借页表把虚拟地址映射到物理内存或其他存储层。
- **Stack Overflow 栈溢出**：调用层数过多等导致栈空间耗尽；与“内存泄漏”不同。

### 5. 计算机网络基础：缩写与端口（【原始技术面经】）

| 协议/术语 | 快速理解 |
|---|---|
| IP | 网络层地址与跨网络转发 |
| TCP | 面向连接、提供可靠有序字节流 |
| UDP | 无连接、尽力而为的数据报传输 |
| HTTP | 基于请求—响应的应用层协议；传统明文 HTTP 常见端口 80 |
| HTTPS | HTTP over TLS，常见端口 443 |
| DNS | 把域名解析到 IP 等记录 |
| Port 端口 | 用于定位主机上的通信端点/服务，单独一个端口号并不保证存在服务 |

**注意**：80/443 是标准**默认/常见端口**，不是“HTTP 永远只能使用 80”。HTTPS 的核心优势是 TLS 提供的认证与加密保护，而不只是把端口从 80 换到 443。

### 6. 软件测试方法（【往届口头追问】）

- **Black-box Testing 黑盒测试**：从规格和输入输出角度验证功能，不依赖内部代码结构。
- **White-box Testing 白盒测试**：关注语句、分支、路径、覆盖率等实现细节。
- **Unit Test 单元测试**：测单个函数/模块；**Integration Test 集成测试**：测模块之间的接口；**End-to-End Test**：测完整业务流程。
- **Performance Testing**：测试吞吐量、延迟、容量等；**Regression Testing 回归测试**：修改之后重新测试既有行为。
- **Boundary-value Analysis 边界值分析**：重点测 `n=0,1`、最大整数、空数组、跨日等条件，和编程笔试的“边界正确性”直接相关。

### 7. 计算机视觉 / 图形学 / VR / AR / MR（【往届技术交流，非笔试高频】）

- **Computer Vision 计算机视觉**：从图像/视频中**理解**场景（识别对象、定位等）。
- **Computer Graphics 计算机图形学**：从几何、材质与场景信息中**生成/渲染**图像。
- **VR**：沉浸式虚拟环境，通常遮蔽现实视觉；
- **AR**：在真实世界视野上叠加数字内容；
- **MR**：现实与虚拟对象更深度地感知与交互融合。具体边界因产品定义不同会变化。

若教授问“设计面向老年人的 VR 应用”，回答应包括**目标用户、核心场景、易用性、安全性、可达性、验证方式**，不只是罗列技术术语。

### 8. 复习自测

1. `malloc` 后丢失指针且没有释放，是什么？**内存泄漏**。

## V2｜进阶与迁移训练【拓展】

### E1. 死锁四条件【拓展】

经典 Coffman 死锁必要条件：互斥、占有且等待、不可抢占、循环等待。破坏任一条件能防止该类死锁。例：线程 1 先锁 A 再锁 B，线程 2 先锁 B 再锁 A；如果双方都占着一把锁等待另一把，就可能死锁。实际开发可按统一顺序获取锁。

### E2. 缓存与局部性【拓展】

CPU Cache 利用**时间局部性**（近期用过的数据可能再次用）和**空间局部性**（访问相邻地址）。遍历二维数组的连续行通常比跨行跳跃更符合数据布局的空间局部性；算法的大 O 相同也可能有显著运行时间差异。

### E3. TCP 三次握手与 UDP 的选择【拓展】

TCP 三次握手概念：SYN → SYN-ACK → ACK 建立连接；它提供重传、顺序与流量/拥塞控制等机制。UDP 不建立此类连接，应用若需要可靠性可能自行处理。实时语音/游戏可能更重视延迟，下载文件通常更重视可靠与完整。

### E4. REST API 与 HTTP 状态码【拓展】

REST 风格常使用 `GET` 获取资源、`POST` 创建/提交、`PUT` 整体替换、`PATCH` 部分更新、`DELETE` 删除。状态码 `200` 成功、`201` 已创建、`400` 请求问题、`401` 未认证、`403` 无权限、`404` 不存在、`500` 服务端错误。面试只需基本语义，不必背所有细分码。

### E5. 软件工程中的性能与安全取舍【拓展】

问“如何设计打车软件”：不要只答 UI。可结合 **匹配效率、地图与定位、容量扩展、数据隐私、支付安全、容灾、无障碍设计、监控与 A/B 测试**。这是把 CS 知识落实到系统问题的一种常见开放题答法。

### E6. 页、TLB 与虚拟内存【拓展】

现代操作系统常把虚拟地址空间按页（page）划分，并借助页表映射到物理页框。TLB 是用于缓存部分地址转换结果的高速结构；缓存命中能避免多次页表访问。**Page Fault 缺页异常**指所需映射/页面不能按当前方式直接完成访问，可能触发操作系统处理；并不总意味着机器发生致命错误。

### E7. 递归、堆内存与大 O 是不同维度【拓展】

算法可能只有 `O(n)` 时间，但若使用递归深度 n，则调用栈空间 `O(n)`；把递归改为显式栈，也不一定把空间降为 `O(1)`，只是换了数据结构。例如 DFS 递归与显式栈 DFS，在最坏情况下都可能保存大量待处理节点。回答时要区分**总内存**、**额外空间**与**结果输出占用空间**。

### E8. 互斥锁与原子操作【拓展】

两个线程分别执行 `counter += 1` 并不一定得到预期的 2 次增加；该操作可能包含读取、加法、写回多个步骤。可使用互斥锁保护临界区，或在适当场景使用语言/平台提供的原子变量。**原子性**在内存并发和数据库 ACID 中都是重要词，但针对的系统层次不同。

### E9. 测试与算法复杂度的交叉题【拓展】

如果一个程序宣称处理 10⁶ 个整数在 1 秒内结束，单次 `O(n)` 扫描通常比双重 `O(n²)` 循环更可行；但算法复杂度不等于实际运行时间，仍受实现、硬件与数据分布影响。测试时应覆盖**典型、边界、最坏输入**，例如排序数组、完全逆序、全相同、空数组及超大 n。

### E10. 图形学与计算机视觉的协作例子【拓展】

自动驾驶系统使用摄像头检测车辆/行人（Computer Vision），用三维场景模拟器生成合成训练数据（Computer Graphics）；如果把识别结果叠加到真实视野，可形成 AR 显示。这不是说三个概念完全相同，而是展示它们如何协作满足实际系统需求。

### E11. 计算机网络的复习问答【拓展】

**Q：输入一个网址发生了什么？** 典型流程包括解析 URL、DNS 解析域名（若需要）、与服务器建立网络连接（如 TCP；若使用 HTTPS 还会涉及 TLS）、发送 HTTP 请求、接收响应、解析/渲染内容。现代 HTTP/3 可使用 QUIC/UDP，故不要断言“所有 HTTP 必须基于 TCP”。普通面试能按这个层次回答已经足够。

**Q：什么是 timeout？** 客户端在规定期限内没有获得期待的响应或完成某项操作；它既可能与网络有关，也可能由服务器负载、锁等待或超时设置造成，不能凭超时就断言“服务器宕机”。

### E12. 数据库事务与内存原子性的对比【拓展】

Memory 和数据库里都可能说 *atomicity*，但语境不同：CPU 原子操作强调某次读—改—写不会被其他并发执行单元观察成不完整的中间步骤；数据库事务原子性强调一组操作**整体提交或整体回滚**。它们都是“不可部分完成”的思想，但保障机制、粒度和持久化需求不同。

**英文追问**：*“A database transaction can group multiple statements into an all-or-nothing unit, while a CPU atomic operation applies to a much smaller memory operation.”*
